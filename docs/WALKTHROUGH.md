# Walkthrough — one message through the whole pipeline

This follows a single message from raw text to final verdict, in order, with the real
numbers our code produces. Every number below was generated by running the pipeline,
not written from memory. If you have never seen this codebase, read this document first.

The message, and the sender it came from:

```
text      : "Aapka SBI khaata bnd ho jayega! Turrant verify karein: http://sbi-kyc-verify.xyz"
sender_id : S00007
```

In English: *"Your SBI account will be closed! Verify at once."* It is a KYC scam, and
it is **deliberately misspelled** — `khaata` for `khata`, `bnd` for `band`, `turrant`
for `turant`. A keyword filter looking for "khata band turant" finds none of them.

The twist, which makes this a good example: `S00007` is a **genuinely innocent
account** (`is_scammer: False`, 0 complaints, 302 days old). So the wording says scam
and the sender history says fine. Watch how the system handles that disagreement.

---

## Step 1 — Normalize the text  ·  `src/preprocess.py`

```python
normalize("Aapka SBI khaata bnd ho jayega! Turrant verify karein: http://sbi-kyc-verify.xyz")
# -> "aapka sbi khaata bnd ho jayega! turrant verify karein: http://sbi-kyc-verify.xyz"
```

Five steps run in order: fold look-alike letters from other alphabets, delete invisible
characters, lowercase, undo leetspeak, collapse padded letter runs
(`normalize`, [src/preprocess.py](../src/preprocess.py)).

Two things it deliberately does **not** do:

- It does not touch digit runs, so `₹10,000` survives. An earlier version collapsed the
  three zeros into one and quietly corrupted every money amount in the dataset.
- It does not "fix" `khaata` → `khata`. Double vowels are legitimate Romanized Hindi
  spelling, and matching them is F6's job, not the normalizer's.

Tokenizing gives 14 tokens:

```
['aapka', 'sbi', 'khaata', 'bnd', 'ho', 'jayega', 'turrant', 'verify',
 'karein', 'http', 'sbi', 'kyc', 'verify', 'xyz']
```

## Step 2 — Measure the wording  ·  F2, `src/f2_hinglish_features.py`

19 numbers come out. The ones that matter here:

| feature | value | what it means |
|---|---|---|
| `hindi_ratio` | 0.43 | nearly half the words are Romanized Hindi |
| `english_ratio` | 0.14 | a little English mixed in |
| `cmi` | 25.0 | the code-mixing index: genuinely mixed, not one language |
| `script_switches` | 3 | it flips between Hindi and English three times |
| `scam_lexicon_hits` | 4 | four words from the scam lexicon |
| `credential_hits` | 3 | it asks for KYC / verification |
| `url_count` | 1 | there is a link |
| `has_suspicious_tld` | 1 | the link ends in `.xyz`, which a bank would never use |
| `caps_ratio` | 0.08 | measured on the **raw** text, since `normalize` lowercases |
| `urgency_hits` | **0** | and here is a miss — see below |

**Note the miss.** `urgency_hits` is 0, even though "Turrant" is exactly a time-pressure
word. The urgency list contains `turant`, not the misspelling `turrant`, so exact
matching fails. This is the gap F6 exists to close.

## Step 3 — Match by sound  ·  F6, `src/f6_phonetic.py`

Every token gets a phonetic code:

```
aapka   -> apk      khaata -> kt       turrant -> trt      verify -> vrf
sbi     -> sb       bnd    -> bd       karein  -> krn      kyc    -> kc
```

`phonetic_code` applies seven rules in order (`src/f6_phonetic.py`). The one doing the
heavy lifting here is rule 5: **drop `n`/`m` before a consonant.** Hindi marks a small
nasal sound with a dot above the letter, English letters have no dot, so people omit it:

```
turrant --(collapse doubles)--> turant --(drop nasal)--> turat --(drop vowels)--> trt
turant  ------------------------------> turat ---------------------------------> trt
```

So the misspelling and the correct spelling land on the same code, and the lexicon
entry matches. F6 reports:

```
phonetic_scam_hits = 3      phonetic_only_hits = 1
```

That `phonetic_only_hits = 1` is one scam word that **exact matching missed and F6
caught** — the whole justification for this functionality, visible on one message.

## Step 4 — Look at the sender's behaviour  ·  F3, `src/graph_builder.py`

The graph has an arrow from each sender to each recipient. For `S00007`:

| feature | value | reading |
|---|---|---|
| `messages_sent` | 7 | a quiet account |
| `out_degree` | 6 | wrote to 6 different people |
| `in_degree` | **12** | and 12 people wrote back — real conversations |
| `unique_recipient_ratio` | 0.86 | mostly different people, but some repeats |
| `clustering` | 0.19 | their contacts know each other: a social circle |
| `burstiness` | 0.006 | spread over weeks, not fired off in an hour |
| `forwarding_ratio` | 0.00 | shares no template wording with anyone |
| `past_reports` | 0 | never reported |
| `account_age_days` | 302 | not a fresh account |

Every one of these says *ordinary person*. `in_degree = 12` is especially telling: nobody
replies to a spam blaster.

## Step 5 — Turn numbers into evidence  ·  `discretize` in `src/f1_bbn.py`

The network is discrete, so each input is cut into `low` / `medium` / `high` using cut
points learned from the **training** data and reused here (re-cutting by the test set's
own quantiles would leak the test distribution):

```
UrgencyCue        = low        (the misspelling defeated the exact urgency list)
CredentialAsk     = high       (3 credential words)
LinkRisk          = high       (a .xyz link)
SenderTrust       = medium     (old account, no complaints)
NetworkCentrality = medium     (quiet, clustered, not bursty)
```

## Step 6 — The Bayesian network reasons  ·  F1, `src/f1_bbn.py`

Evidence is added one piece at a time, strongest first. This list **is** the explanation
— it is the computation, not a story about it:

```
Prior (before reading anything):                      0.160
a request for a secret (OTP, PIN, KYC) is HIGH:       0.280
the riskiness of the link is HIGH:                    0.730
how trustworthy the sender account looks is MEDIUM:   0.620
how the account sits in the message network is MEDIUM:0.500
time pressure in the wording is LOW:                  0.500
```

Read that as a story: we start mildly suspicious (16% of messages are scams). The
credential request nudges it up. The `.xyz` link pushes it hard to 0.73. Then the
sender's decent history pulls it **back down** to 0.62, and their ordinary network
behaviour pulls it to 0.50.

Final BBN score: **0.499 → SAFE** (threshold 0.50). The network hedges, and it is
*wrong* — but you can see exactly why: two of its five clues describe the account, and
this account looks innocent.

## Step 7 — The ensemble decides  ·  F4, `src/f4_ensemble.py`

Three opinions on the same message:

| detector | score | verdict |
|---|---|---|
| Bayesian network (F1) | 0.499 | SAFE |
| feature model (34 fused features) | 0.841 | FRAUD |
| **stacked ensemble (F4)** | **0.965** | **FRAUD** |

The feature model reads all 34 features, including the ones the BBN compresses away,
and is confident. The stack learned weights of **+9.6 for the feature model and +2.0
for the BBN**, so it follows the feature model and corrects the BBN's hedge. This single
message is the argument for fusion: the explainable model alone would have let it
through.

## Step 8 — What would have changed the verdict?  ·  F7, `src/f7_counterfactual.py`

The BBN called it SAFE, so F7 explains what would have made it suspicious. It tries all
one-variable changes first (and only moves to pairs if none works), so the answer is
genuinely minimal:

```
If how trustworthy the sender account looks had been LOW,
    this message would have been marked FRAUD (0.50 -> 0.92).
If how the account sits in the message network had been HIGH,
    this message would have been marked FRAUD (0.50 -> 0.86).
```

In other words: *the only thing saving this message is the sender's clean record.* That
is a precise, auditable statement about the decision — and exactly what an appeals
process needs.

## Step 9 — Attack it  ·  F8, `src/f8_adversarial.py`

A scammer would now try to defeat us. F8 rewrites this message five ways and re-scores
it. Across held-out scam messages, recall against the homoglyph attack is:

| defence | recall |
|---|---|
| none | 0.707 |
| `normalize()` only | 0.888 |
| `normalize()` + F6 phonetic | **0.937** |

And against Hindi respellings — the attack already visible in this very message —
normalization alone scores 0.831 while adding the phonetic layer recovers it to 0.894.
Normalization cannot help there, because `turrant` is not a trick: it is simply another
correct spelling. Only matching by sound works.

## The whole path in one line

```
raw text
  -> normalize()                 preprocess.py
  -> 19 text features            f2_hinglish_features.py
  -> + 2 phonetic features       f6_phonetic.py
  -> + 13 sender/graph features  graph_builder.py  (joined by f3_fused_features.py)
  -> discretize to low/med/high  f1_bbn.py
  -> P(Fraud) + explanation      f1_bbn.py
  -> stacked with feature model  f4_ensemble.py
  -> counterfactual              f7_counterfactual.py
  -> robustness check            f8_adversarial.py
```
